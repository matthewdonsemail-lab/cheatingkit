# How it works

CheatingKit reconstructs a task from the user's own local conversation history. The flow has five parts: capture, normalize, index, retrieve, and supply cited context.

## The context problem

A task may span multiple sessions and harnesses. A later prompt such as “continue the loader issue” does not restate the original target, earlier findings, or a correction that narrowed the work. A model switch or a warning response can also interrupt the apparent continuity of the session. The system therefore preserves the event sequence instead of treating the latest message as the entire task.

## The approach

1. Import Claude Code and Codex JSONL and Hermes SQLite messages into a common schema, retaining source IDs, tool calls, models, and ordering.
2. Use [MiniLM](/docs/models/minilm) and BM25 to index overlapping conversation windows. Use [GLiNER 2.5](/docs/models/gliner) to extract candidate goals, targets, constraints, and completion criteria from user messages.
3. Search when a new request arrives, then compare retrieved statements with later user corrections. Assistant and tool text can provide evidence but cannot supersede a user's instruction.
4. Build a bounded context pack containing the selected source passages, message IDs, and uncertainty. A harness integration passes that context alongside the unchanged user request.
5. Record warning and model-switch observations against the same timeline so the user can inspect what happened.

For the exact cursor, index, and recovery design, see [Local context and search](/docs/models/context-pipeline).

## Provider proxy preview

The Codex provider proxy is a separate integration. `ck proxy setup` asks for an OpenAI Responses-compatible provider, model ID, and API key environment variable, then configures Codex with a dedicated local provider whose WebSocket transport is disabled. The resident server relays HTTP `/v1/responses` requests and SSE streams to the selected upstream using that provider key. `ck proxy remove codex` restores the prior Codex provider and model.

Request analysis is off by default, so the task provider receives the original request bytes. Run `ck proxy analysis setup` to select a **separate** Responses-compatible analysis model and choose `suggest` or `apply`. Restart the proxy after changing this setting. The analysis model receives the latest plain user message and bounded, source-linked local session evidence. `suggest` forwards the original request and records proposed wording. `apply` replaces only that latest user text in the forwarded request; the selected task model, previous conversation, tools, and other fields stay in place. A failed analysis forwards the original request. Inspect the latest decision with `ck proxy analysis last`, or turn analysis off with `ck proxy analysis off` and restart. The configuration stores an environment variable name for the analysis key, never the key itself. [Issue #10](https://github.com/matthewdonsemail-lab/cheatingkit/issues/10) tracks additional harness and provider adapters.
