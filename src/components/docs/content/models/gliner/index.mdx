# GLiNER 2.5 screening

CheatingKit pins [GLiNER 2.5 Small](https://huggingface.co/fastino/gliner2.5-small-v1) as a local extraction model. The pin is kept exact so it can be wired when a supported loader is available. It is **not currently used in the running CLI**: no worker calls it, and no extracted rows are stored.

## Current state

The architecture that would use it is specified but not built:

- a local worker receives user-authored text and an extraction schema
- it returns candidate goals, targets, constraints and completion criteria
- each candidate carries its value, confidence, model and schema revision, and source message ID
- candidates are evidence for the context resolver, not a decision about whether an earlier goal still applies

For the working CLI, the local models in use are MiniLM (embedding and search) and, in the RLM environment, MiniLM prototype scoring plus `Xenova/nli-deberta-v3-xsmall` for zero-shot property extraction. See [The RLM environment](/docs/repl).

## Why the pin stays

GLiNER 2.5 is `gliner2` architecture, which transformers.js does not map; a zero-shot pipeline on those files falls back to a bare encoder. Removing the pin would lose the artifact before a loader that supports it exists. Keeping it exact means enabling it later needs no re-download and no ambiguity about which files were tested.

The long-term case for local extraction is unchanged: structured goals and constraints on CPU, without sending transcripts to a hosted service, where semantic similarity alone cannot say which words state the target or limit the work.
