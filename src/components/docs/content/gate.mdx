# The per-message gate

CheatingKit has two delivery mechanisms that work together. Prompt hooks inject source-linked history into a request while the harness keeps its own provider and credentials. The **per-message gate** is the second mechanism: when a harness routes through the local proxy, the gate decides whether the request should be forwarded before any provider call happens.

## Where the gate sits

A request travels from the harness to the local proxy, through the gate, and only then to the provider. An allowed request is forwarded with the harness's own credentials. A blocked request returns a local response and the provider is never contacted.

The gate runs on every eligible request across Codex Responses, Claude Messages, and Hermes Chat Completions. It reads the same local corpus and context builder that the hooks use. Prompt hooks alone do not enforce the gate; enforcement requires the harness to use the proxy.

## What the gate checks

For each message the gate keeps the original request intact and evaluates the outlined task and any proposed wording together:

- **Scope and authorization.** It assesses whether the task is within the scope defined for this user and whether the authorization the task depends on is present. Local history is evidence, not proof of authorization.
- **Independent validation.** A separate evaluation compares the original and proposed text against every goal, scope boundary, and constraint. Concealed intent, added authority, dropped constraints, and changed objectives fail validation.
- **Context.** Retrieved source-linked history is attached to every evaluation, so the decision is made against the recorded task rather than the latest sentence alone.

The gate returns `allow`, `block`, or `needs_clarification` before the provider call. Blocks, clarification requests, evaluator failures, malformed evaluator output, and unresolved validation failures all make zero provider calls. Enforced blocks return HTTP 403; clarification returns HTTP 422.

## Revisions

When validation finds that a rewrite lost fidelity, the gate can request a bounded revision — at most two — to restore the original goal and constraints or clarify wording. Revisions exist to preserve meaning, not to influence what the provider will decide. If fidelity is still unresolved after the limit, the gate blocks.

## Records

Every decision is linked to the request's attempt record as `gateDecision`. It contains the original request body, the original and proposed text, the retrieved evidence and its source IDs, each scope and validation result, every revision, and the termination reason. Request bodies are stored locally for this audit; authentication headers never are. Failed provider streams keep their embedded error code and message, with cyber warnings labelled `potential_cyber_warning` and transport failures `stream_error`.

## Rollout

The gate has three modes: `off` disables evaluation, `observe` records the decision and forwards the original bytes, and `enforce` applies the decision. The default is `observe`.

```sh
ck proxy analysis setup
ck proxy start --gate-mode enforce
```

`CHEATINGKIT_GATE_MODE=off|observe|enforce` selects the mode for a launched proxy. Stop a running proxy before changing modes; `ck proxy status` reports the active mode. `ck proxy attempts [request ID]` shows the gate decision beside the observed outcome.

Without a configured analysis model, `observe` records an evaluator error and forwards the original request; `enforce` blocks. Unsupported requests without eligible plain user text also fail closed in enforce mode. Set `CHEATINGKIT_GATE_MODE` in the environment used by your launcher to retain the selected mode after a restart.

Native credentials are preserved even when a task-provider key is configured. To intentionally substitute the configured destination provider's credentials, use `--credential-mode provider` on start/install or set `CHEATINGKIT_CREDENTIAL_MODE=provider`. Reinstall an existing Codex route to update its authentication setting. Protocol translation uses the selected destination provider's credentials.

ChatGPT-signed-in Codex uses the native Responses destination `https://chatgpt.com/backend-api/codex`; API-key sign-in uses `https://api.openai.com/v1`. Configure the destination that matches the harness's existing authentication. Passing through a ChatGPT token to the API-key destination does not change it into an API key.

Before merging an integration change, install the candidate build and test its real request path. Prompt the user to restart Codex after route changes, then confirm the restarted session appears in `ck proxy attempts` with its gate decision. Tests and CI do not replace this installed verification.

## Limits

The gate checks a task against locally defined scope and authorization criteria. It does not predict or optimize for a provider's decision, and it does not decide whether an activity is safe in a general sense. Local observations describe what happened in earlier sessions; they are not a guarantee about a new request.
