# The per-message gate

CheatingKit has two delivery mechanisms that work together. Prompt hooks inject source-linked history into a request while the harness keeps its own provider and credentials. The **per-message gate** is the second mechanism: when a harness routes through the local proxy, the gate decides whether the request should be forwarded before any provider call happens.

## Where the gate sits

A request travels from the harness to the local proxy, through the gate, and only then to the provider. An allowed request is forwarded with the harness's own credentials. A blocked request returns a local response and the provider is never contacted.

The gate runs on every eligible request across Codex Responses, Claude Messages, and Hermes Chat Completions. It reads the same local corpus and context builder that the hooks use. Prompt hooks alone do not enforce the gate; enforcement requires the harness to use the proxy.

## What the gate checks

For each message the gate keeps the original request intact and evaluates the outlined task and any proposed wording together:

- **Scope and authorization.** It assesses whether the task is within the scope defined for this user and whether the authorization the task depends on is present. Local history is evidence, not proof of authorization.
- **Independent validation.** A separate evaluation compares the original and proposed text against every goal, scope boundary, and constraint. Concealed intent, added authority, dropped constraints, and changed objectives fail validation.
- **Context.** Retrieved source-linked history is attached to every evaluation, so the decision is made against the recorded task rather than the latest sentence alone.

The gate returns `allow`, `block`, or `needs_clarification` before the provider call. Blocks, clarification requests, evaluator failures, malformed evaluator output, and unresolved validation failures all make zero provider calls. Enforced blocks return HTTP 403; clarification returns HTTP 422.

## Revisions

When validation finds that a rewrite lost fidelity, the gate can request a bounded revision â€” at most two â€” to restore the original goal and constraints or clarify wording. Revisions exist to preserve meaning, not to influence what the provider will decide. If fidelity is still unresolved after the limit, the gate blocks.

## Records

Every decision is linked to the request's attempt record as `gateDecision`. It contains the original request body, the original and proposed text, the retrieved evidence and its source IDs, each scope and validation result, every revision, and the termination reason. The audit also records the shared rewrite context and exact forwarded request body. For Codex requests with a project directory, retrieval is restricted to that project before ranking; the initial rewriter receives the harness hook evidence, and revisions reuse the same retrieved evidence. Enforce mode carries that reviewed history into the task request as explicitly untrusted data. Historical reports do not establish current repository state: the task assistant must inspect the repository. A validated rewrite is not a task-completion result. Request bodies are stored locally for this audit; authentication headers never are. Failed provider streams keep their embedded error code and message, with cyber warnings labelled `potential_cyber_warning` and transport failures `stream_error`.

## Rollout

The gate has three modes: `off` disables evaluation, `observe` records the decision and forwards the original bytes, and `enforce` applies the decision. The default is `observe`.

```sh
ck proxy analysis setup
ck proxy start --gate-mode enforce
```

`CHEATINGKIT_GATE_MODE=off|observe|enforce` selects the mode for a launched proxy. Stop a running proxy before changing modes; `ck proxy status` reports the active mode. `ck proxy attempts [request ID]` shows the gate decision beside the observed outcome.

Without a configured analysis model, `observe` records an evaluator error and forwards the original request; `enforce` blocks. Unsupported requests without eligible plain user text record why and are forwarded untouched in observe, and fail closed in enforce. Set `CHEATINGKIT_GATE_MODE` in the environment used by your launcher to retain the selected mode after a restart.

## Contract

Evaluation output is not free-form JSON. `src/cli/proxy/analysisSchema.yaml` is a versioned contract with five operations (`rewrite`, `scope`, `consistency`, `validate`, `revise`), each an exact shape with typed values and explicit lengths. The rewrite operation is a union: `proposed` carries `proposedText`, while `unchanged`, `needs_context` and `refused` carry `proposedText: null`, so an unchanged proposal keeps the host's exact bytes. Every other operation is a flat object whose fields are all required.

Validation is deterministic and runs before any result is used. A missing field, unknown field, string where a boolean belongs, empty rationale, missing transition or an out-of-range value fails closed as an evaluator error; it never becomes an allow. The outcome-to-next-step map (`transitions`) is the only route through the gate, so a recognized but unmapped outcome stops the request instead of continuing by default.

The file also carries the bounded policies: fallback defaults off, an unbound required task is rejected before evaluation, revisions stop at two, one rate-limit retry is allowed, and calls are paced. Each decision record and rewrite attempt stores the contract `version` and content `hash`, so an audit shows which contract judged it.

Prompt text in `analysis.js` and `gate.js` restates the contract; the YAML is authoritative. Change the YAML first, then the prompts, and update the parsers together.

Native credentials are preserved even when a task-provider key is configured. To intentionally substitute the configured destination provider's credentials, use `--credential-mode provider` on start/install or set `CHEATINGKIT_CREDENTIAL_MODE=provider`. Reinstall an existing Codex route to update its authentication setting. Protocol translation uses the selected destination provider's credentials.

ChatGPT-signed-in Codex uses the native Responses destination `https://chatgpt.com/backend-api/codex`; API-key sign-in uses `https://api.openai.com/v1`. Configure the destination that matches the harness's existing authentication. Passing through a ChatGPT token to the API-key destination does not change it into an API key.

Before merging an integration change, install the candidate build and test its real request path. Prompt the user to restart Codex after route changes, then confirm the restarted session appears in `ck proxy attempts` with its gate decision. Tests and CI do not replace this installed verification.

## Limits

The gate checks a task against locally defined scope and authorization criteria. It does not predict or optimize for a provider's decision, and it does not decide whether an activity is safe in a general sense. Local observations describe what happened in earlier sessions; they are not a guarantee about a new request.


## Decision consistency

Before a scope allow can proceed to independent fidelity validation, a separate evaluator call checks that the decision agrees with its rationale and the actual request. It receives the same reviewed evidence plus the recorded scope evaluation. A contradictory or unsupported allow, malformed consistency result, disagreement, timeout or evaluator error blocks forwarding in enforce mode. The audit retains both evaluations and a `scope_consistency_failed` termination reason when applicable. This check does not revise the request or retry a safety block.

This adds one analysis-model call per candidate whose scope decision is allow, with the existing 30-second per-call timeout. A scope block or clarification terminates immediately. There remains one initial rewrite proposal and at most two fidelity revisions. The consistency check is model-based and cannot guarantee detection of every semantic contradiction; malformed outputs and reported disagreements always fail closed.


## Durable tasks and original-request fallback

The resident analysis path now binds requests to durable project tasks. A concrete initial instruction or explicit issue reference establishes a task; a session binding or an unambiguous active project task resolves a continuation. Unknown or ambiguous continuations remain unbound and are rejected in enforce mode. You can inspect task identity with `ck task list` and `ck task show ID`, explicitly start one with `ck task start --goal TEXT`, or bind a session with `ck task bind ID --session-id SESSION`. A request can name `continue task ID` to select a specific task.

Task goals, ordered user directives, observations, source IDs and immutable context hashes persist locally. Later user directives remain visible even as the current action changes. The proposer, gate and provider share the same reviewed task snapshot. Task state does not grant permissions. Acceptance criteria require successful host receipts linked to the task and criterion; ordinary provider responses remain observations. Automatic correlation of arbitrary harness checks to acceptance criteria is not implemented.

Explicit GitHub issue/PR references import versioned source snapshots through the authenticated `gh` executable. This optional source capability requires GitHub CLI and access to the linked repository. Refresh is cached for five minutes; comment and character bounds and excerpt omissions are recorded. Source errors stop requests requiring that specification. Selection by headings/recency is a bounded heuristic, not proof that all relevant requirements were recovered. A source budget is not an authorization mechanism.

Original-request fallback is disabled by default. `ck proxy analysis fallback on` explicitly enables evaluating the unchanged original when the optional proposal is refused/unavailable; all required task binding, scope, consistency and fidelity gates still apply. `ck proxy analysis fallback off` disables it again. Restart the proxy after changing this setting. A missing required evaluation or unbound task never falls through to the provider. Typed proposal statuses distinguish a rewrite from a refusal, missing context or invalid output.

The current runtime preserves direct user instructions rather than claiming autonomous semantic planning or guaranteed task completion. Generative analysis uses the configured provider; the local CPU embedding model remains retrieval infrastructure. No provider is selected automatically to obtain approval.


## Analysis provider rate limits

Rewrite and gate calls share a bounded, serialized provider/model queue. A 429 may be retried once when `Retry-After` fits within two seconds. Longer delays are surfaced immediately; exhausted rate limits establish a bounded cooldown so queued requests do not hammer the provider. Authentication failures, known billing/quota errors and model safety refusals are not treated as transient rewrite retries.

In enforce mode, an unavailable analysis provider returns HTTP 503 with `Retry-After`, `analysis_rate_limited`, the affected stage and the request ID. The attempt records `analysis_unavailable`, not a safety denial. No task-provider call occurs. The configured original-request fallback remains off by default and cannot skip an unavailable required gate. Provider request payloads omit unrelated tool schemas and duplicate evidence renderings; task state and reviewed evidence remain attached.
